# Security Policy & Security Checks

## Security is the highest priority

For VergissMeinNicht, **security takes precedence over convenience, speed of implementation, and feature count**.

The application manages authenticated users, collaborative procedures, audit trails, security-sensitive household/operational routines, and potentially shareable entry links. A weakness in login or authorization can expose far more than a normal todo list.

Authentication, sessions, MFA, authorization, Workspace isolation, account recovery, Knot tokens, imports, uploaded files, stored third-party credentials, outbound connections, and audit integrity must be treated as security-critical.

This file is normative and must evolve with the application.

**Every agent must review this file before implementing security-sensitive behavior.**

**Whenever a task introduces a new attack surface, credential type, permission boundary, sensitive input, or sensitive data flow, the agent must add or update checks in this file before marking the task complete in `steps.md`.**

## 1. Authentication baseline

### Password login
- [x] Use a mature maintained authentication library/framework. (Better Auth 1.7.6, reviewed 2026-09-26; its HTTP handler is not mounted, see "local password login and sessions".)
- [x] Never store plaintext or reversibly encrypted passwords.
- [x] Use Argon2id or a currently recommended reviewed equivalent. (Argon2id via `@node-rs/argon2`; Better Auth's default scrypt is replaced.)
- [x] Parameter choices are documented and tested. (m=64 MiB, t=3, p=1, 32-byte output, 16-byte salt; `packages/auth/src/password-hashing.ts` + test.)
- [x] Compare secrets using library primitives designed for the purpose. (Argon2 `verify`; cookie signatures verified by Better Auth.)
- [x] Login errors do not reveal whether an account exists. (One `401 invalid_credentials` for every failure; unknown users still cost one hash.)
- [x] Login attempts are rate-limited. (10/min per client address, 10/15 min per account.)
- [x] Successful login rotates the session identifier. (New session per login; a session presented with the login request is revoked.)
- [x] Password changes invalidate relevant old sessions as policy requires. (Self-service change and recovery reset delete all sessions of the user in the same transaction; the changing client gets a fresh session.)
- [x] Password values never appear in application logs, traces, analytics, or error payloads. (Verified by log capture in `apps/server/src/http/auth.test.ts`.)
- [x] New passwords: 15–128 characters (NIST SP 800-63B-4 single-factor minimum), no composition rules, NFKC-normalized before hashing.
- [x] Breached/common-password blocklist. (Offline: 60 003 most common 15+ character passwords from public breach corpora, bundled with the server, compared in NFKC/lower-case/no-space form; plus repetitive/sequential patterns and passwords made mostly of the service name or the account's own email/name. Checked at invitation acceptance, password change and recovery; passwords never leave the server. Update procedure: `packages/auth/data/README.md` — 13.3.)

### TOTP MFA
- [x] TOTP is built in and user-activated (optional) for V1 accounts; the MFA requirement is evaluated by a central server-side policy so enforcement (e.g. for ADMIN) can be added later. (`requiresTotpChallenge()` in `packages/domain/src/mfa.ts`.)
- [x] Seed generated with a CSPRNG. (160 bits via `otpauth` → `crypto.randomBytes`.)
- [x] Enrollment is not active until the user proves a valid OTP. (Unconfirmed enrollment expires after 10 min.)
- [x] TOTP seed is treated as highly sensitive data. (AES-256-GCM at rest with `DATA_ENCRYPTION_KEY`, bound to the user id; shown once at enrollment; never logged.)
- [x] Submitted OTP values are never logged. (Verified by log capture.)
- [x] Verification attempts are rate-limited. (Per client, per account, 5 per challenge, account lock after 10 consecutive failures escalating to 24 h.)
- [x] Time-window handling is intentionally bounded. (±1 step of 30 s; each step accepted once per account — replay protection.)
- [x] Recovery codes are high entropy. (10 × 80 bits.)
- [x] Recovery codes are stored hashed. (SHA-256 per code.)
- [x] Recovery code use is one-time and atomic. (Conditional update; concurrency tested.)
- [x] MFA enable/disable/reset is audited. (Enable/disable/use/regenerate/lock and admin/operator TOTP reset.)
- [x] Enabling TOTP and regenerating recovery codes require recent re-authentication. (Current password in the same request.)
- [x] Disabling TOTP requires re-authentication plus a valid OTP or recovery code.
- [x] For a TOTP-enabled account, a password-authenticated session that has not passed the TOTP challenge cannot access authenticated app resources. (No session exists before the challenge; only a challenge cookie scoped to `/api/auth/mfa`.)
- [x] The session is rotated after a successful TOTP challenge. (The full session is created only then; enabling/disabling TOTP revokes all sessions of the user.)
- [x] No "remember this device" / trusted-device bypass.

### Future external login: Apple / GitHub (planned), Microsoft (possible)

- [ ] External subject/provider ID mapping is explicit.

## 2. Sessions and browser security

- [x] Session IDs are opaque and generated with sufficient entropy. (32 chars from a 62-symbol alphabet via `crypto.getRandomValues`, ≈190 bits; cookie value HMAC-signed with `AUTH_SECRET`.)
- [x] Server-side session state is authoritative. (`sessions` table; `cookieCache` disabled; user status re-checked on every request.)
- [x] Production session cookie is `Secure`. (`__Secure-vmn.session_token`.)
- [x] Session cookie is `HttpOnly`.
- [x] `SameSite` policy is intentional and documented. (`Strict`: the SPA only needs the cookie on same-site `fetch` calls; cross-site navigations such as email links load the public shell first.)
- [x] Cookie Domain/Path are no broader than necessary. (No `Domain`, `Path=/`.)
- [x] Session rotates after login and security-sensitive privilege changes. (Login, TOTP enable/disable, password change and account recovery: yes — all sessions of the user are replaced. Account disabling deletes every session in the same transaction (2.7). Workspace role changes need no rotation: no role is cached in the session, every request re-reads the Membership. Reviewed 2026-09-29: no server-admin grant/removal flow exists — **when one is added it must replace the user's sessions** (review trigger).)
- [x] Logout invalidates server-side session.
- [x] Idle/absolute expiration policies are documented. (Idle 7 days, refreshed at most daily; absolute 30 days, enforced per request — `SESSION_POLICY` in `packages/auth`.)
- [x] CSRF protection covers state-changing cookie-authenticated operations. (Every non-GET/HEAD/OPTIONS request needs `Origin` = `PUBLIC_ORIGIN`, missing `Origin` rejected; JSON-only bodies; `SameSite=Strict`.)
- [x] Authentication library endpoints are not exposed wholesale: only allow-listed server routes call Better Auth (`/api/auth/sign-in`, `/sign-out`, `/session`); tests assert other Better Auth paths return 404.
- [x] Disabled users cannot start sessions; disabling deletes their sessions and pending sign-in challenges at once (2.7), and any leftover session is revoked on the next request.
- [x] CORS is deny-by-default / narrowly configured. (No CORS plugin registered: same-origin only; any future CORS needs review.)
- [x] Sensitive responses are not cached publicly. (`Cache-Control: no-store` on all `/api/*`.)
- [x] Production uses HTTPS. (Config rejects non-https `PUBLIC_ORIGIN` except loopback; the Compose deployment terminates TLS in Caddy with automatic certificates, 10.1.)
- [x] HSTS enabled when deployment topology makes it safe. (For https origins, one year by default, `HSTS_MAX_AGE`; no `includeSubDomains`/`preload` so other services on the domain are unaffected, 10.3.)
- [x] Content-Security-Policy is defined. (`default-src 'self'`, `script-src 'self'`, `style-src 'self'` and `font-src 'self'` without `'unsafe-inline'` since 8.3, `object-src 'none'`, `frame-ancestors 'none'`; the e2e flow fails on any CSP violation.)
- [x] Clickjacking prevented via CSP `frame-ancestors`.
- [x] `X-Content-Type-Options: nosniff`.
- [x] Strict `Referrer-Policy`, especially around Knot URLs. (`no-referrer` header + meta tag; verified on `/knot/{token}` by e2e, 7.1.)

## 3. Authorization and ACLs

- [x] Authorization happens server-side for every protected operation. (`requireUser` + `authorizeWorkspace`/server-admin checks in every use-case. `apps/server/src/http/route-security.test.ts` checks the registered route table itself, so every new route is covered: pinned public routes, 401 without session, 404 for non-members on every Workspace route, 403 for non-admins on every `/api/admin/*` route — 13.2.)
- [x] UI-hidden buttons are never the authorization mechanism. (The web client receives capabilities only to adapt its UI; every request is re-authorized.)
- [x] Workspace membership checked for resource access. (`authorizeWorkspace` in `packages/application/src/workspaces/use-cases.ts` reads the Membership on every call; non-members get the same 404 as unknown ids.)
- [x] Role/capability checked for the requested operation. (Capabilities, not role strings; mutations re-check the actor's current role and ACTIVE status inside the write transaction.)
- [x] Child resources cannot bypass parent Workspace checks. (Memberships, Procedures, Sections, Steps, Runs, RunSteps, Knots: every query is scoped by the route's Workspace id plus the child id; a child id from another Workspace behaves like an unknown id; Section/Step ids in a save must already belong to that Procedure, enforced in the transaction and by a composite FK. The route-table test uses every child id of Workspace A under Workspace B → 404, nothing changes; it found and fixed Procedure history answering `200 []` instead of 404 — 13.2.)
- [x] Object identifiers are opaque but are not treated as authorization. (UUIDv4 Workspace ids; knowing an id grants nothing.)
- [x] Guest/User/Editor/Admin policies are centrally defined. (`packages/permissions`: one role → capability table incl. Procedure/Run capabilities (3.2), exact-matrix test; matrix documented in steps.md 3.2.)
- [x] Cross-Workspace access has negative tests.
- [x] Horizontal privilege escalation has negative tests. (Admin of Workspace A cannot manage members of Workspace B; members cannot see other Workspaces.)
- [x] Vertical privilege escalation has negative tests. (GUEST/USER/EDITOR cannot add, re-role, remove or rename; self-promotion refused; Workspace ADMIN ≠ server admin.)
- [x] Membership/role changes are audited. (`WORKSPACE_CREATED`, `WORKSPACE_RENAMED`, `MEMBERSHIP_ADDED`, `MEMBERSHIP_ROLE_CHANGED`, `MEMBERSHIP_REMOVED` in `security_events`, same transaction.)
- [x] Removing a member invalidates/updates active access promptly. (No cached authorization: the next request with the same session is denied. SSE streams re-check membership before every delivered change and at every 20 s heartbeat — Step 6.1.)
- [x] Workspace creation goes through one capability (`canCreateWorkspace`: ACTIVE server admins only).
- [x] Every Workspace keeps at least one ACTIVE member with `workspace.members.manage`; enforced inside the membership transaction.
- [x] Lists (15.3) have their own capabilities: `list.view` (every role) and `list.edit` (USER, EDITOR, ADMIN — GUEST stays read-only). Every List and item lookup is scoped by the route's Workspace id and List id; a foreign or deleted List and a foreign or removed item answer like unknown ids (`packages/database/src/list-use-cases.test.ts`, `apps/server/src/http/list.test.ts`, route-table test).
- [x] Assignment grants no access. (An Assignee of a Schedule or Occurrence (14.1) must be an ACTIVE member who can see the Workspace's Procedures when assigned; completing, skipping, starting and linking are authorized by the actor's own capabilities only — a GUEST Assignee can see but not act. Negative tests in `schedule-use-cases.test.ts` and `apps/server/src/http/schedule.test.ts`.)

## 4. Knot links

Canonical shape:
`/knot/{opaque-token}`

- [x] Token generated by CSPRNG with adequate entropy. (256 bits, `crypto.randomBytes`, base64url.)
- [x] Token is never placed in query parameters. (Path `/knot/{token}` for the page; the API takes it in the JSON body of `POST /api/knots/resolve`.)
- [x] Token values are redacted from application/proxy logs where possible. (`/knot/…` and `/api/knots/…` paths redacted by the request serializer; reverse-proxy logs must be configured by the operator — 10.x.)
- [x] Stored token is hashed where practical. (SHA-256 only; the link is shown once at creation.)
- [x] Knot has explicit scope/target and permission. (Exactly one Procedure or Run of its Workspace, DB CHECK; managed with `knot.manage`.)
- [x] Knot can expire. (1–365 days or never.)
- [x] Knot can be revoked. (Final, audited, record kept; DB trigger forbids un-revoking.)
- [x] Expired/revoked tokens have negative tests.
- [x] Knot possession does not replace authentication under current requirements. (Resolution requires a session; 401 without one.)
- [x] User authorization is checked after Knot resolution. (`procedure.view` / `run.view` in the Knot's Workspace, and again by every request of the target page.)
- [x] Referrer policy prevents accidental propagation. (`no-referrer`; the app also replaces the history entry after opening.)
- [x] Error responses do not disclose sensitive target details before authorization. (One `404 knot_not_found` for every failure.)

## 5. Input and output safety

- [x] Validate all inputs at server trust boundaries. (Params, query and body of every route are parsed by strict Zod schemas before use; imports by the strict import-export parser; domain parsers re-validate — reviewed 2026-09-29.)
- [x] Use schema validation for API payloads. (`z.strictObject` everywhere: unknown fields rejected.)
- [x] Parameterize SQL / use safe query builder or ORM. (Drizzle; `sql` templates bind interpolated values as parameters.)
- [x] Never concatenate user input into SQL. (`sql.raw` only in schema CHECK constraints from compile-time constants; `prepare`/`exec` only with constant strings — guarded by `packages/database/src/sql-safety.test.ts`.)
- [x] Escape output according to rendering context. (React text rendering only; no HTML sinks — guarded by `apps/server/src/http/web-output-safety.test.ts`; emails are text-only; JSON responses.)
- [x] Do not accept arbitrary HTML by default. (Procedure text is plain text; the web client renders it as text, never via `innerHTML`.)
- [x] User-selectable icons are trusted icon keys, not arbitrary uploaded SVG/HTML. (`PROCEDURE_ICONS`, validated in the domain; in the database every icon column references the `procedure_icons` table since migration 0019 — keys are only ever added by migrations. Artwork comes from one registry in the web bundle (`apps/web/src/procedure-icons.tsx` with its generated part `icon-catalog.generated.ts`: Tabler Icons plus drawn icons, static named imports only — the generator runs at development time, never at runtime or from user input, and refuses to drop a key it produced before); stored data holds keys, never artwork, markup, URLs or library component names, and no icon is ever loaded or built from data. `AppIcon` resolves keys with an own-property lookup (so `constructor`/`__proto__` cannot resolve to anything) and shows a neutral fallback for unknown values; writes and imports still refuse unknown keys (domain + foreign key). Tests: `packages/database/src/procedure-icons.test.ts` (table = key list), `apps/web/src/procedure-icons.test.tsx` (fallback for unknown/malicious values), `procedure-copy-use-cases.test.ts` (imports with library names, prototype keys, markup or URLs as icons are refused and write nothing).)
- [x] Apply sensible text/array/file-size limits. (Procedures: title 120, description 4000 code points, ≤10 tags × 32, ≤1000 per Workspace; ≤50 Sections, ≤200 Steps per Procedure, 1 MiB body limit on Procedure saves; scheduled items: ≤5 reminders, 0–30 days / 1–48 hours, ≤731 days ahead, ≤1000 open per Workspace, 4 KiB bodies; bot token ≤128, notification bodies 1 KiB; global 64 KiB body limit; coarse transport bounds in the Zod schemas. Keep extending per feature — reviewed 2026-09-29.)
- [x] Lists (15.3) are bounded: ≤100 Lists per Workspace, ≤300 items per List (deleted ones do not count), name 80 / item 120 / unit 16 code points, quantity a positive decimal of ≤5 digits and ≤3 decimals, 4 KiB bodies; text is plain text with control and bidi characters refused (domain + DB CHECKs).
- [x] Reject malformed UUIDs/tokens/state transitions. (Lower-case UUIDv4 path/body ids; malformed, upper-case and nil ids in every path parameter → 400/404, never 5xx (route-table test); tokens length/alphabet-checked before hashing; state transitions by the domain state machine with compare-and-set.)
- [x] Drag/drop order input is validated, authorized, and bounded. (Reordering is client-side only; the result is saved through the 4.2 Procedure save: `procedure.edit`, ids must belong to the Procedure, ≤50 Sections / ≤200 Steps, revision check.)

- [x] Emails are normalized (trim, NFC, lower-case) before storage/lookup; uniqueness is enforced on the normalized value by a unique index.
- [x] Emails with invisible or broken characters are rejected (control, format — zero-width, direction marks, soft hyphen —, private-use, unassigned, lone surrogates, U+FFFD, non-ASCII spaces): they would create look-alike accounts or addresses nobody can type (found on the first Unraid install, 0.1.0-beta.3).
- [x] Display names reject control and bidi override/isolate characters so audit snapshots cannot be visually spoofed.
- [x] Critical invariants (id shape, normalized email, status enum) are also enforced by DB CHECK constraints.
- [x] Validation errors carry stable codes and never echo the rejected input.
- [x] Auth/invitation API bodies are validated with strict Zod schemas (unknown fields rejected, string length bounds); global body limit 64 KiB, 4 KiB on auth routes; only `application/json` is parsed.
- [x] Link tokens travel in JSON bodies for API calls, never in API URLs.

### JSON import
- [x] Treat imports as hostile input. (`packages/import-export`: strict parse, then the regular create path with all domain rules.)
- [x] Require/validate `schemaVersion`. (Only `1`; checked before the schema; anything else → `unsupported_schema_version`.)
- [x] Validate full shape before persistence. (Strict Zod schema, then domain normalization of every field before the transaction.)
- [x] Reject invalid references/state/type values. (Unknown keys at every level rejected; enums/kinds validated; the format carries no references.)
- [x] Bound input size and collection counts. (1 MiB body, coarse array bounds in the schema, exact domain limits, per-Workspace Procedure limit.)
- [x] Do not allow imported IDs to overwrite unauthorized existing records. (Documents contain no ids; any id field is rejected; all ids are server-generated.)
- [x] Import is transactional or fails cleanly. (One `IMMEDIATE` transaction with the audit event; tests assert nothing is created on failure.)

### Document files, previews and other hostile content (steps.md section 16)
_Planned 2026-10-01, nothing implemented. These rules differ from instruction images (14.3) on purpose: there the upload is discarded and only a processed, metadata-free JPEG is kept; here the original is kept unchanged. The 14.3 controls stay as they are._
- [x] **Originals are stored and returned byte-for-byte, including embedded metadata** (H6): nothing rewrites, re-encodes, rotates or strips an original; a download has the SHA-256 of the upload. Consequence, accepted by decision: EXIF/GPS, author names and other embedded data reach every member including guests — stated on the upload screen and in the user guide. (16.1: the upload is streamed into the store and only ever read afterwards; tests compare SHA-256 and find the GPS data again. The notice is on the Add document screen and in the user guide since 16.2; the e2e flow asserts it.)
- [x] The content is identified and validated; file name and declared type are never trusted. Allow-list: PDF, JPEG, PNG, HEIC/HEIF. Executables, scripts, HTML, SVG, archives, office files and polyglots are refused and nothing is stored. The instance admin may narrow the list, never widen it beyond what the server can validate. (16.1: signature at offset 0, then the format's own parser; images containing HTML markup anywhere are refused; `documentFormats` accepts only known formats — domain, use-case and a database trigger.)
- [x] Size is enforced while receiving (50 MB initially, instance-admin setting); pixel, page-count, time, memory and concurrency limits apply before and during every decode; processing is queued, never unbounded. (16.1: counted in the stream, 1–100 MB setting; 50 MP checked from the header; 500 preview pages; 30 s per parser job; one parser job (time-limited; memory bounded by the WebAssembly module at 2 GiB, plus a best-effort watchdog) and two libvips decodes at a time; three uploads per person at once; previews one page at a time.)

- [x] File names are data: normalised, length-limited, control and bidi characters refused, never used as storage paths; download and archive names are generated by the server (no traversal, no absolute or reserved names). (16.1: stored names and download names. 16.4: every path segment of an export comes from `exportSegment` / `planExportPaths` — titles, Folder names and file names alike.)
- [x] Export archives: server-generated paths, streamed, size-bounded; the HTML index is static, escapes every value and contains no script, no remote resource and only relative links. (16.4: yazl stream with files opened one at a time; 2 GB / 5 000 files; `documentsIndexHtml` — a test checks the set of tags and attributes, every link, and hostile titles, names and notes.)
- [x] Malware scanning is a documented choice (HT6): either none, relying on "never executed, download only", or an optional separate `clamd` — never a required service. (16.1, HT6: **none**. A stored file can still be malicious for the program that opens the download — VMN does not scan; said in `deployment.md` and to be said in the user guide with 16.2.)
- [x] Search and sort parameters are bound parameters with bounded lengths; items in Trash or in another Workspace are never found and reveal no count. ## 13. Locked V1 authentication policy

The following choices are mandatory V1 behavior:

- public registration is disabled;
- account creation begins with an ADMIN-created invitation to a required email address;
- invitation acceptance must prove/use that invited email;
- TOTP is optional and user-activated, but built in from V1 (not mandatory for now); the pre-MFA state holds no session at all (challenge token only);
- an account with TOTP enabled receives no normal application/Workspace access until the TOTP challenge succeeds;
- whether TOTP is required is decided by a central server-side policy, so mandatory enforcement can be introduced later without redesign;
- password recovery is admin-assisted only in V1;
- TOTP reset (lost device) is admin-assisted, audited, removes the TOTP credential and recovery codes, and invalidates existing sessions;
- there is no unauthenticated password-reset email flow in V1;
- there is no "remember this device" MFA bypass in V1 unless separately approved;
- Apple and GitHub login are planned but deferred (Microsoft possible later) and require a new account-linking/MFA security review before implementation.

### Security check: invite-only account bootstrap
**Threat surface:** invitation theft, token replay, account squatting, email mismatch, invitation enumeration.  
**Controls required:** CSPRNG token, expiry, single use, revocation, token hashing where practical, target-email binding, generic error handling, audit trail, no token logging.  
**Negative tests:** expired invite; replayed invite; revoked invite; wrong email; unauthorized invite creation.  
**Secrets/data involved:** invite token, email address.  
**Logging review:** invitation token must be redacted.  
**Authorization review:** only ADMIN capability can issue/revoke invitations.  
**Open risks:** email delivery channel security is external to the application.  
**Status (2026-09-26):** complete (steps.md 2.2/2.3).  
**Implemented controls:** 256-bit CSPRNG token, SHA-256 at rest, `/invite/{token}` path (redacted in logs), TTL (default 72 h, max 720 h), supersede-on-reissue, single-outcome DB constraint, generic resolve error, ACTIVE-server-admin check inside use-cases, token never returned to the inviter, atomic security events, append-only event table, bootstrap refused once an admin exists and limited to one live link; acceptance is POST-only, validates the link before hashing, and creates User + credential + acceptance + events in one `BEGIN IMMEDIATE` transaction (single use under concurrency); bootstrap links are rejected at resolve and accept time once any server admin exists; acceptance never creates a session; admin endpoints require a session and the ACTIVE-server-admin check in the use-case.  
**Negative tests (implemented):** replay, concurrency (3 parallel accepts → 1 user), expired/revoked/superseded, email taken in between, bootstrap after admin exists, unknown/malformed tokens, extra body fields, USER calling admin list/issue/revoke, unauthenticated admin calls, missing/foreign `Origin`.  
**Reviewed:** 2026-09-26

### Security check: optional user-activated TOTP
**Threat surface:** challenge bypass through API routes, SSE, Knot resolution, stale session, alternate login path; enrollment race; attacker with a stolen session enabling TOTP to lock the owner out; attacker disabling TOTP (downgrade); recovery-code brute force.  
**Controls required:** explicit restricted pre-MFA session state for TOTP-enabled accounts; centralized middleware/policy denies normal resources until the TOTP challenge is satisfied; re-authentication to enable TOTP or regenerate recovery codes; re-authentication plus OTP/recovery code to disable; rate limits; audit events for enable/disable/recovery-code use/regeneration/admin reset.  
**Negative tests:** pre-MFA session of a TOTP-enabled account cannot access Workspace API, subscribe SSE, resolve Knot target details, or call admin routes; cannot promote session via client flag; TOTP cannot be disabled without OTP/recovery code; TOTP cannot be enabled without re-authentication; used recovery code is rejected.  
**Secrets/data involved:** TOTP seed, OTP values, recovery codes.  
**Logging review:** seed, OTP and recovery codes never logged.  
**Authorization review:** MFA gate must be server-side and centralized.  
**Open risks:** accounts that have not enabled TOTP (including ADMIN accounts) are protected by password only — consider an enforcement policy for ADMIN later; future OAuth/OIDC login paths require explicit policy because provider flows may not automatically pass through credential 2FA hooks.  
**Status (2026-09-26):** implemented (steps.md 2.4), except admin reset (2.5).  
**Implemented controls:** own use-cases on reviewed primitives (Better Auth `twoFactor` plugin rejected: no replay protection, reversible non-atomic backup codes, password-only disable, trust-device feature); no session before the challenge — the password step yields only a 256-bit challenge token (hash at rest, 5 min, 5 attempts, single use, cookie `HttpOnly`/`Secure`/`Strict`, `Path=/api/auth/mfa`); full session issued by Better Auth only after a valid factor; replay protection via last accepted time step; account lock after 10 consecutive wrong codes (15 min doubling to 24 h) with recovery codes still usable; per-client and per-account rate limits; seed encrypted (AES-256-GCM, HKDF from `DATA_ENCRYPTION_KEY`, user id as AAD); 80-bit recovery codes hashed, atomic single use; password for enable/regenerate, password + factor for disable; all sessions replaced on enable/disable; security events for every step.  
**Negative tests (implemented):** `packages/database/src/mfa-use-cases.test.ts`, `apps/server/src/http/mfa.test.ts` — challenge cookie (also disguised as session cookie) rejected by session, account and admin routes; client `mfaVerified` flag rejected; forged/missing/expired/exhausted/used challenge; replay; disable without factor; enable without password; used recovery code; concurrent recovery-code use; disabled user after password step; no secrets in logs. SSE/Knot routes do not exist yet — their tests must include the challenge-only case.  
**Reviewed:** 2026-09-26

### Security check: admin-assisted recovery
**Threat surface:** malicious/compromised admin, stolen admin session, privilege abuse, stolen reset token, active-session persistence, downgrade of a user's TOTP, social engineering of admins.  
**Controls required:** explicit ADMIN capability, short-lived single-use recovery flow, audit trail, session invalidation, TOTP credential and recovery codes removed when TOTP is reset.  
**Controls implemented (2026-09-26, Step 2.5):** server-admin capability checked in the use-case; step-up (admin password + admin TOTP if enabled) per recovery; no self-recovery via the admin path; link emailed only to the account's own address and never shown to the admin; 256-bit token, SHA-256 at rest, 60 min, single use, superseded on re-issue; TOTP-only reset additionally needs the user's current password; completion atomically applies the reset, deletes TOTP + recovery codes, invalidates MFA challenges and deletes every session of the user; per-client and per-admin rate limits; security events for issue/supersede/complete/reset; operator CLI fallback attributed to `cli:admin-recover`; self-service password change revokes all sessions.  
**Negative tests:** non-admin, disabled admin, wrong admin password, missing admin TOTP, self-target, unknown/disabled/TOTP-less target; used/expired/superseded/malformed token; TOTP reset without or with wrong current password; old sessions rejected after completion; concurrent completion (`packages/database/src/recovery-use-cases.test.ts`, `apps/server/src/http/recovery.test.ts`).  
**Secrets/data involved:** recovery token (link), new password.  
**Logging review:** `/recover/{token}` and `/api/recoveries/{…}` redacted in request logs; tokens travel in JSON bodies for API calls; verified by log capture.  
**Authorization review:** separate server-admin capability, independent of Workspace roles; enforced in `issueAccountRecovery`.  
**Open risks:** an admin who also controls the user's mailbox (or an operator with shell access) can take over accounts — inherent to admin-assisted recovery, visible in the audit trail; users who lost mailbox access need an out-of-band operator process; no admin UI yet; administrative social engineering remains an operational risk (admins should verify the requester through a second channel before starting a recovery).  
**Reviewed:** 2026-09-26

### Security check: application skeleton (Step 1.1)
**Threat surface:** HTTP server baseline (headers, static file serving, SPA fallback), SQLite file handling, dependency supply chain, CI.

### Security check: local password login and sessions (Step 2.3)
**Threat surface:** credential guessing (online, distributed), account enumeration, password hash theft/cracking, session theft/fixation, CSRF on login/logout/admin actions, open redirects, hidden endpoints of the authentication library (sign-up, profile/email change, password reset, account linking), spoofed client IPs defeating rate limits, disabled accounts keeping access, leaking tokens/passwords into logs or responses.

**Secrets/data involved:** passwords (transient), Argon2id hashes (`accounts.password`), session tokens (`sessions.token`, cookie), `AUTH_SECRET` (cookie HMAC), client IP and user agent in `sessions`.  
**Logging review:** request logs contain method, redacted URL, status; failed sign-ins log an event marker without email; Better Auth messages are forwarded without structured arguments ("User not found", "Invalid password"); unexpected errors logged as type + stack frames only. Verified by capturing all log output in the HTTP test suite.  
**Authorization review:** session → ACTIVE User resolution is centralized in `authenticate()`/`requireUser` (`apps/server/src/http/session.ts`), which is also the seam for the 2.4 TOTP gate; admin capabilities are checked in the use-cases.  
**Open risks:** behind a reverse proxy without `TRUSTED_PROXIES` (available since 10.3, preset in the Compose deployment) all clients share one address and per-client limits become global (DoS of sign-in by one attacker); per-account limit lets an attacker temporarily block a known account's sign-in (bounded to 15 min windows); session tokens are stored unhashed (a DB leak plus `AUTH_SECRET` allows session forgery — protect both; rotate `AUTH_SECRET` after suspected compromise); no breached-password blocklist; in-memory rate-limit state resets on restart (sensitive limits persisted since 2.9); password change and privilege-change session rotation not yet implemented; `BETTER_AUTH_TELEMETRY` env var would override the explicit telemetry opt-out — do not set it.  
**Reviewed:** 2026-09-26

**Logging review:** neither key nor seeds are logged; `Secret` wrapper redacts the key.  
**Authorization review:** only the MFA use-cases open sealed secrets, for the owning user.  
**Open risks:** key and database together (same host) defeat the encryption — it protects stolen DB files/backups, not a compromised server; losing or changing the key disables every enrolled authenticator (users fall back to recovery codes / admin reset in 2.5); no rotation tool yet; development without a configured key uses a per-process key.

### Security check: instruction images (Step 14.3)
**Threat surface:** the first file-upload and file-download surface: hostile files (SVG with script, PDF/HTML polyglots, decompression bombs, huge pixel counts, animated/multi-page files, malformed data aimed at image decoders); metadata leaks (GPS, device, owner names in EXIF/XMP/comments); reading another Workspace's images by id or by content hash; images served as something a browser executes; uploads bypassing or racing the Workspace quota; disk exhaustion; deleting files still referenced by historical Runs; Run history silently changing when a template image is replaced; backups missing or corrupting images; hostile Procedure archives (path traversal, symlinks, duplicates, zip bombs, lying sizes, hash mismatches, unexpected entries); libvips memory-safety bugs; licence obligations of the native binaries.

Processing with sharp/libvips (`packages/media`): HEIC detected from the `ftyp` box and refused with a clear message, format identified from the content (JPEG/PNG/WebP only — SVG, GIF, PDF and everything else refused), header dimensions checked before decoding (≤50 MP; `limitInputPixels` as a second guard), animated/multi-page refused, `failOn: 'error'`, at most two images processed at once (libvips concurrency 1, cache off); EXIF orientation applied, then output without any metadata, flattened on white, sRGB, ≤1600 px without upscaling, JPEG 80→60 then ≤1024 px, ≤500 KB or refused. Only the processed JPEG is stored — never the upload. The browser additionally converts photos to a ≤1600 px JPEG before sending (so EXIF/GPS do not leave the phone and iPhone HEIC works where the browser decodes it); this is a convenience only. Files are content-addressed (`/data/media/<xx>/<sha256>.jpg`, `0700`/`0600`, atomic temp-file + fsync + rename, paths built only from a validated hash). Metadata rows are per Workspace (unique Workspace + hash; immutable, triggers); Steps reference images of their own Workspace only (checked in the save transaction; foreign or unknown ids → `invalid_item_reference`), with a required 1–200 character caption (domain rules + triggers keep image and caption together). Serving: `GET /api/workspaces/:ws/images/:id` requires `procedure.view` in that Workspace and resolves the id within it — a hash is never accepted and an id of another Workspace is "not found"; answers are `image/jpeg`, `nosniff`, `Content-Disposition: inline`, `Cache-Control: no-store` (stricter than the planned `private`), CSP `img-src 'self' data: blob:` (blob: for offline copies and the browser conversion). Run snapshots copy the reference and caption at start; `run_steps` image columns are immutable (trigger); images referenced by any Step or Run can never be deleted (foreign keys). Quota (D11a): usage = distinct images of the Workspace referenced by a Step (incl. restorable deleted Procedures) or a Run, plus uploads of the last 24 h not yet referenced; checked and inserted in one `IMMEDIATE` transaction (two parallel uploads that fit only one at a time: exactly one succeeds); an image that was left unused past the grace period can no longer be attached (it is no longer charged); `replacing` excludes the replaced image when no Run uses it; quota changes only by server admins, from the four fixed choices, audited as `WORKSPACE_IMAGE_QUOTA_CHANGED`, never deleting anything. Housekeeping (hourly) deletes unreferenced rows older than 24 h, then files no row uses, and orphan files older than 24 h. Archives (`packages/import-export`, yauzl): body ≤125 MB, ≤201 entries, read into memory only (never written to archive paths), yauzl name validation (no absolute paths, `..` or backslashes), no directories, symlinks, special files, encryption or duplicates, only `procedure.json` and manifest-listed `images/<n>.jpg`, per-entry and total size limits counted while streaming, compression-ratio limit, declared sizes validated, SHA-256 checked, one image per existing Step; read only after authorization; every image is processed again and charged to the target Workspace; all-or-nothing (images registered for a failed import are released). Export archives are deterministic (fixed timestamps; no ids, users or Workspace data). Backups: see §8. Licences: `third-party-notices-server.txt` in the image lists every runtime package incl. the libvips component licences.
**Negative tests:** `packages/media/src/image-processor.test.ts` (orientation 6 + GPS/EXIF removed, no upscaling, transparency, size floors, SVG, PDF, empty, HEIC, >10 MB, 20 000 × 20 000 PNG bomb, animated WebP, GIF, JPEG/HTML polyglot), `packages/media/src/file-media-store.test.ts` (permissions, atomic write, hash-only paths), `packages/database/src/image-use-cases.test.ts` (roles, cross-Workspace ids, captions, snapshot retention after replace/delete/housekeeping, DB-level immutability and FK protection, grace-period gap, quota full / concurrent / dedup across 30 Runs / lowering / replacement), `packages/database/src/backup-media.test.ts` (fresh-volume restore, missing and altered files, shared store pruning), `packages/import-export/src/procedure-archive.test.ts` (traversal, absolute, backslash, symlink, directory, duplicate, unlisted and non-image entries, missing image, hash mismatch, unknown Step, two images for one Step, zip bomb, ratio, lying sizes, not a ZIP, extra manifest fields, too many entries, oversize), `apps/server/src/http/image.test.ts` (401/403/404, origin, content types, 413/415/422, headers, metadata gone, archive round trip into another Workspace charged there, broken archive), `apps/server/src/http/route-security.test.ts` (all new routes), e2e (file-picker upload, caption, execution thumbnail, viewer with axe, archive export/import), container smoke test (processing in the read-only image).
**Secrets/data involved:** photos of people's homes and equipment (Workspace-confidential, like Procedure text), captions; no metadata is kept.
**Logging review:** nothing about images is logged except housekeeping counts (`imageFiles`); refusal reasons are stable codes, never file content or names.
**Authorization review:** HTTP authenticates and parses (`apps/server/src/http/image-routes.ts`, archive routes in `procedure-routes.ts`); decisions in `packages/application/src/media/use-cases.ts` and `archive.ts`; in-transaction guards and Workspace scoping in `packages/database/src/image-repository.ts` and `procedure-repository.ts`.

### Security check: document files (Step 16.1)
**Threat surface:** the second file-upload surface and the first that **keeps what was uploaded**: hostile files of four formats aimed at their parsers (PDF, JPEG, PNG and the HEIC container — malformed structures, decompression and pixel bombs, pages of absurd size, endless content streams, thousands of pages); files that are something else (executables, HTML, SVG, archives, office documents) under an accepted name; polyglots that are an image and a web page at once; active content in PDFs (JavaScript, embedded files); stored files served back so that a browser runs them in the app's origin; embedded metadata (GPS, device, author) reaching every member, guests included; reading or downloading files of another Workspace by id or by content hash; uploads by roles that may not write; disk exhaustion (50 MB bodies, many uploads, previews of 500 pages, uploads abandoned half-way) and memory or CPU exhaustion by one request; uploads racing the storage limit; slow uploads holding connections; file names as path traversal, header injection or log content; a backup missing or silently holding altered originals; files deleted while a backup still needs them; a new large dependency (a PDF renderer) and its licence; the patent situation of HEVC, had a HEIC decoder been shipped.
**Controls added:** upload only with `document.manage` (USER, EDITOR, ADMIN; `authorizeWorkspace` **before the first byte is accepted**, re-checked inside the registering transaction), same-origin (`Origin` check), one streamed `application/octet-stream` body on this route only (other declared types → 415, never parsed), at most 300 uploads per 15 minutes and three at once per person. **Receiving:** the body is written to `/data/documents/.staging/<random>` while it is counted and hashed — never buffered in memory, never in `/tmp`; the size limit (instance setting, 1–100 MB, default 50 MB) ends the upload at the first byte beyond it; a refused upload gets its answer while at most 32 MB of the rest are read and thrown away, then the connection is closed; ordinary requests keep a 30-second deadline, an upload has 15 minutes and a connection silent for one minute is closed. **Validation** (`packages/media`, `createDocumentFileProcessor`): the format is the signature at offset 0 (`%PDF-`, JPEG, PNG, an ISO `ftyp` box with an HEVC image brand) — never the name or a declared type — followed by the format's own parser: images by sharp/libvips from the header (format must match, HEIF must be HEVC-coded — AVIF is refused —, animated PNG refused, ≤50 MP checked before anything is decoded); JPEG and PNG are then **decoded completely once** for the preview (`failOn: 'error'`; a file that cannot be decoded is refused); **HEIC is validated from its container alone and never decoded** — no HEVC decoder is shipped (HT1), so a HEIC has no preview (`preview.unavailable: "format"`) and is otherwise a normal file; an image containing `<script`, `<html`, `<!doctype html` or `<iframe` anywhere is refused as a polyglot; PDFs are opened by MuPDF (page count ≥ 1, password protection, JavaScript / embedded files / open or additional actions detected) and their first page is drawn (a PDF that cannot be drawn is refused). **Isolation of the PDF parser:** MuPDF runs as **WebAssembly** — a memory-safety bug stays inside the module's linear memory — in **one worker thread, one job at a time**; a job is ended by terminating the thread after 30 s, and the next job gets a new thread; the thread is stopped when idle; its console is silenced and MuPDF's warnings are dropped, so a file cannot write to the server log; ICC handling is off; nothing in it opens a network connection or writes a file. **Memory, stated exactly:** what always holds is the module's own maximum — its WebAssembly memory cannot grow beyond the 2 GiB it declares — plus a 256 MB cap on the thread's JavaScript heap and one in-memory copy of the file (≤100 MB); with one job at a time that is about 2.4 GB at worst. A **watchdog** additionally terminates the thread when the whole process has grown by more than 1.5 GB since the job began; it polls every 200 ms from the main thread and is therefore **best effort, not a limit**: a fast allocation between two polls, or a busy main thread, gets past it, and unrelated work in the process counts towards it. It does **not** by itself prevent a parser from exhausting the server's memory; a memory limit on the container does (`deployment.md`). **Originals are never changed and never rendered:** the staged file is renamed into the content-addressed store (`/data/documents/<xx>/<sha256>`, `0700`/`0600`, fsync, paths built only from a validated hash) and from then on only read; `GET …/original` answers with `Content-Disposition: attachment`, the content type of the *detected* format, `nosniff`, `no-store`, `Content-Security-Policy: sandbox; default-src 'none'`, and a download name **generated by the server** (path parts, quotes, reserved and control characters removed, Windows device names avoided, ≤120 characters, always ending in an extension of the detected format — `invoice.html` that is a JPEG downloads as `invoice.html.jpg`; RFC 5987 encoding). **Previews** are separate files: re-encoded JPEGs, upright, flattened, sRGB, ≤2400 px, **without any metadata**, PDF pages drawn at 200 dpi within 2400 px whatever size the page claims, without annotations or form widgets and without a JavaScript engine; at most 500 pages; made in the background one page at a time, resumable after a restart from the file's `PENDING` state, given up after three failed attempts; the CSP is unchanged (ordinary same-origin images). **File names** are data (`X-File-Name` header, percent-encoded; directory part dropped, NFC, 1–255 code points, control / invisible / bidi characters refused, DB CHECK) and never a path; they are not in the address, so no access log holds them. **Authorisation of every read:** session, `document.view` in the route's Workspace, lookup by Workspace id + file id — a foreign or unknown id and a missing preview answer one `404 file_not_found`, a non-member `404 workspace_not_found`; the hash is accepted nowhere and appears in no response; responses carry display names, not user ids. **Storage limit:** `workspaces.storage_quota_bytes` (default 5 000 000 000, a usage limit; since 16.4 the ceiling of the Workspace's combined storage, shared with instruction images — see the 16.4 check); usage = originals + derived files of the Workspace with identical content counted once, computed inside the `IMMEDIATE` transaction that inserts the row (two uploads that fit only one at a time: exactly one succeeds, also on separate connections); a full Workspace refuses new originals, lets previews stop (`PARTIAL`) and never affects reading; lowering deletes nothing. **Instance settings** `documentMaxFileBytes` and `documentFormats`: ACTIVE server admins only (re-checked in the transaction), validated by the domain and by database triggers, recorded in `INSTANCE_SETTINGS_CHANGED`; they apply to new uploads only. **Database:** `document_files` rows are immutable except the preview progress (trigger), derived rows immutable, no cascades, CHECKs for format, hash shape, sizes and names. **Housekeeping** (hourly): rows nothing references and older than 24 h are deleted with their derived rows, then files no row uses, orphan files and staged uploads older than 24 h. **Backups:** see §8. **Dependencies:** see below.
**Negative tests:** `packages/media/src/document-file-processor.test.ts` (signature at offset 0 only; `.exe` renamed `.pdf`, SVG, HTML, ZIP, shell script, GIF, WebP, AVIF, TIFF refused; JPEG+HTML, mixed-case `<ScRiPt>`, markup in a PNG text chunk, a token across the reader's chunk boundary refused while a photo with EXIF/GPS passes; 20 000 × 20 000 PNG refused from the header; a bomb within the pixel limit, a truncated JPEG, a bare signature, a fake PDF, an empty HEIC container; a 200-inch PDF page drawn at 2400 px; locked PDF not drawn; JavaScript and embedded-file PDFs flagged and drawn as images; a job stopped by the time limit and the watchdog's stop path (forced), the processor working again afterwards; a HEIC accepted from its container with damaged image data, refused with a broken container or an absurd size, and never given a preview; preview without EXIF/GPS and upright while the original keeps its bytes), `packages/media/src/document-file-store.test.ts` (cut off at the first chunk beyond the limit, nothing kept; broken upload leaves nothing; modes; hash-only paths; sweep of old staged files only), `packages/database/src/document-file-use-cases.test.ts` (GUEST and non-member refused on upload, every read under another Workspace or with the hash or an unknown id; demotion between check and write; disabled actor; refused files leave no row, no file, nothing staged; limits and formats changed by non-admins or to invalid values; database triggers for settings, immutability and the delete guard; storage full, lowering, exactly-one-of-two on separate connections, previews stopping when full; 500-page cap; restart and three-attempt cap; three uploads at once per person; housekeeping keeps what is fresh or still used), `apps/server/src/http/document-file.test.ts` (401 without session, 403 without or with a foreign `Origin`, 403 GUEST upload, 404 for non-members / foreign ids / guessed ids on metadata, original, thumbnail and page alike, 400 for the hash and malformed page numbers; ### Security check: Folders, Documents and the tool switch (Step 16.2)
**Threat surface:** a new set of Workspace resources over the most sensitive content so far: reading, changing, moving, deleting or restoring Folders and Documents of another Workspace by id (IDOR), also indirectly — a Folder of Workspace A as parent or target in Workspace B, a file of A as a page in B, a type of A on a Document of B; a file attached to two Documents; GUESTs changing content; roles below ADMIN switching tools; a tool that is "off" still answering somewhere, or switching it off destroying data; a Folder moved into its own subtree (a cycle that detaches or loops the tree), also by two concurrent moves; lost updates between people editing the same Document; restore bringing back more than was deleted, overwriting or merging with what exists now, or resurrecting content under a parent that no longer exists; "uploaded by / at" rewritten after the fact; history that does not match the change; deleted content silently lost — or silently still present; stored XSS or visual spoofing through names, titles, notes, tags and type names; unbounded Folders, Documents, pages, types or bodies; client-chosen ids or fields smuggled into creation; the uploader's hidden metadata reaching other members without anyone having been told.
**Controls added:** **Tool switch:** `workspace_tools`; `workspace.tools.manage` (ADMIN only) in the central policy; `authorizeTool` in every document, folder, type, trash and document-file use-case — membership first (non-member → `404 workspace_not_found`), then the switch (`404 tool_not_enabled` for every role, ADMIN included), then the capability; the switch is read again inside every write transaction; switching writes one row and an audit event and touches no content; there is no per-user setting. **Capabilities:** reads `document.view` (all roles), writes and the Trash list `document.manage` (USER, EDITOR, ADMIN), each write re-checking the actor's current role and ACTIVE status inside its `IMMEDIATE` transaction. **Scoping:** every lookup is by Workspace id + id; unknown, foreign and trashed ids answer one `404 folder_not_found` / `document_not_found` / `document_type_not_found` / `file_not_found`; and the database itself refuses cross-Workspace references through composite foreign keys (Folder → parent, Document → Folder, Document → type, page → Document, page → file — each together with the Workspace id). A file is a page of at most one Document (unique index); attaching a file of another Document is refused (`file_in_use`). **Tree integrity:** the rules are pure functions (`packages/domain/src/document.ts`: placement, depth ≤ 10, sibling names compared NFKC + case-insensitively, restore target and name) applied to the whole tree read inside the transaction, so two concurrent moves cannot form a cycle; a trigger refuses any `parent_id` that leads back to the Folder, a CHECK refuses self-parenting, a partial unique index refuses duplicate live sibling names. **Concurrency:** `revision` on Folder and Document; rename, move, edit and page changes are compare-and-set (`409 document_conflict`), never last-writer-wins. **Trash:** deleting sets `deleted_*`; a Folder's deletion marks exactly what was live below it with that deletion's id, so restore brings back that set and nothing deleted separately; a restored Folder is renamed "(restored)" rather than merged when its name is taken, and goes to the nearest existing ancestor when its parent is gone — and the answer says so; the database refuses `DELETE` on Documents and Folders outright (no code path, and no expiry, removes them — permanent deletion is 16.4). Files of trashed Documents are kept and stay charged. **Facts that cannot change:** who uploaded a Document and when (trigger); a Folder's creator; ids and Workspace of every record. **Audit:** every change writes its event (`FOLDER_*`, `DOCUMENT_*`, `DOCUMENT_TYPE_*`, `WORKSPACE_TOOL_*`) in the same transaction — a failing audit insert rolls the change back; metadata holds titles, names, counts, ids and the *names* of changed fields, never notes or file content; previews and downloads are not events. **Input:** strict Zod bodies (unknown fields such as `id`, `workspaceId`, `uploadedBy` refused), 64 KiB limit, lower-case UUIDv4 ids; domain normalisation with length bounds and control / bidi refusal for names, titles, type names and tags, notes as plain multi-line text, calendar-date and year validation, built-in type keys from a fixed list; DB CHECKs repeat the bounds. Limits: 1000 Folders, 50 000 Documents, 50 files per Document, 100 own types, 200 Documents per move, 200 Documents listed per Folder (replaced in 16.3 by pages of fifty). **Output:** responses carry display names — no user ids, emails or storage names; the web client renders everything as text (React escaping; `web-output-safety.test.ts` still passes); the CSP is unchanged. **Metadata notice:** the Add document screen states, before any file is chosen, that files are kept exactly as uploaded, may contain location or author data, and can be downloaded by everyone in the Workspace including guests; the user guide says the same.
**Negative tests:** `packages/domain/src/document.test.ts` (field rules; tree rules; a seeded random walk of 4800 creates, moves, deletes and restores asserting after every step: no cycle, no live Folder under Trash, no duplicate sibling name), `packages/database/src/document-use-cases.test.ts` (tool off for every role incl. ADMIN, only ADMIN switches, switch re-checked in the write, data kept; GUEST refused on all fifteen write and Trash operations; a non-member and Home's ids under Office on every operation; cross-Workspace parent, target, file and type; DB-level refusal of cross-Workspace references, of a cycle, of deleting, of changing upload facts; stale revisions; `file_in_use`; restore outcomes incl. rename and nearest ancestor; no expiry after 400 days; files of trashed Documents survive housekeeping while a removed page's file does not; demotion between check and write; audit failure rolls back; two concurrent cycle-forming moves on separate connections — exactly one succeeds), `apps/server/src/http/document.test.ts` (404 `tool_not_enabled` on every route for every role before enabling and after disabling; 401 / 403 without `Origin` / 403 GUEST / 404 outsider on all fourteen writes; Home's ids under Office → 404; strict bodies and stable codes; nothing created by refused requests; no ids, emails or hashes in responses; nothing of a Document in the captured log), `apps/server/src/http/route-security.test.ts` (all 21 new routes: session, non-member, child ids under another Workspace with the tool on in both, malformed ids; Home unchanged afterwards), `packages/permissions/src/policy.test.ts`, e2e (tool absent → page not found; switch on / off; the metadata notice; upload with one refused file; keyboard reordering; byte-identical downloads; HEIC without preview; Trash and restore with rename; axe at 1280, 390 and 320 px in Light and Dark; no CSP violation).
**Secrets/data involved:** titles, notes, tags, dates and types of household documents; Folder names; display-name snapshots of who uploaded, modified and deleted. No credentials.
**Logging review:** no new log output. Request logs hold routes with ids; titles, names and notes travel in JSON bodies, which are not logged (asserted on the captured log). Audit metadata: titles and names, never notes or content.
**Authorization review:** HTTP authenticates and parses (`apps/server/src/http/document-routes.ts`); decisions in `packages/application/src/documents/documents.ts` and `tools.ts` (`authorizeTool`); in-transaction guard, tool re-check, Workspace scoping and tree rules in `packages/database/src/document-repository.ts`.
**Open risks:** (1) **No permanent deletion yet (16.4):** what is in Trash stays, stays charged and cannot be removed by anyone through the app — a document uploaded by mistake (or one that must be erased) can only be hidden until then. (2) A page removed from a Document is deleted by housekeeping within the hour and cannot be brought back; the confirmation says the file is deleted. ### Security check: finding Documents (Step 16.3)
**Threat surface:** search, filters and sorting as a read surface over the most sensitive Workspace content: a query returning — or counting, or offering as a filter value — Documents of another Workspace or in Trash; a Folder, type or cursor of another Workspace used as a filter; SQL injection through the search text, tags, the uploader name, the sort or the direction; `LIKE` wildcards turning a search into a pattern oracle; a forged or replayed cursor reaching rows outside the listing; response time that depends on other Workspaces' content (a timing side channel); expensive queries as a way to exhaust the server (long search texts, many terms, deep paging, the filter-value scan); search words — themselves sensitive ("diagnosis", a name) — leaking through logs, addresses or referrers; the filter list of uploaders disclosing member identities to guests; derived columns that drift from the text they index, so that edited or deleted wording is still found.
**Controls added:** **No new capability and no new write path:** `findDocuments` and `documentFilterValues` are reads behind the same `authorizeTool(…, 'document.view')` as every Documents read (membership → tool switch → capability; non-member `404 workspace_not_found`, tool off `404 tool_not_enabled`). **Scope first:** the repository builds every listing, count and filter-value query from `workspace_id = ?` and `deleted_at IS NULL`, then adds the filters; a Folder filter is resolved among the live Folders of that Workspace (unknown, foreign or trashed → one `404 folder_not_found`), a type id or uploader name of another Workspace simply matches nothing. **Injection:** all values are bound parameters through Drizzle; search words become `LIKE ? ESCAPE '\'` patterns with `%`, `_` and `\` escaped, so everything typed is literal text; `sort` and `dir` are validated against fixed lists in the domain and then choose between fixed column references — no request text is ever part of a statement (the `sql-safety` test still holds: no `sql.raw`, no interpolated statement strings). **Bounds:** search ≤ 100 characters and ≤ 8 words (refused beyond, not cut), ≤ 10 tags, year 1900–2200, uploader ≤ 200 characters without control or bidi characters, a strict query schema that refuses unknown parameters, a fixed page size of 50 (no client-chosen limit), cursor ≤ 8 KiB of base64url; the global API rate limit applies. **Cursor:** the last row's sort value and id, base64url JSON; only its *shape* is validated against the order in use (`400 invalid_cursor` otherwise) — it is a position inside a query that is already scoped, so a forged one can skip rows of the caller's own listing and nothing else; it carries no authority and reveals nothing the page before did not show. **Counts:** the total is the count of the same scoped query; filter values (years, tags, uploader names) are read from live Documents of the Workspace only. **No cross-Workspace work (HT7):** search is a scan of the asking Workspace's own rows — FTS5 was measured and rejected partly because its shared index made one Workspace's response time depend on another's content. **Derived columns:** `title_key`, `tag_keys` and `search_text` are written in the same statement as the content they derive from (create and edit), required by a trigger on insert, and filled by `migrate` for older rows; they contain nothing the Document does not. **Output:** results are the 16.2 summaries — display names, no user ids, emails or storage names; the uploader filter works on the recorded display name precisely so that no member id is handed to a guest. **Search words in transit:** they travel in the query string of a same-origin `GET`; the request log redacts query strings (asserted on the captured log), `Referrer-Policy: no-referrer` keeps the address from other sites, and the Compose proxy writes no access log.
**Negative tests:** `packages/database/src/document-search-use-cases.test.ts` (Trash and the other Workspace never found by search, tag, uploader or any order, and not counted; filter values free of both; a Folder in Trash, of another Workspace or unknown → not found, with and without sub-folders; hostile search texts, tags and uploader names — `' OR 1=1 --`, `UNION SELECT`, `DROP TABLE` — find nothing and harm nothing; `%`, `_` and `\` are literal; unknown sorts and directions incl. `title; DROP TABLE documents` refused; too long, too many words, bad type, year, folder, tags refused; malformed cursors of twelve shapes and a cursor of another order refused; another Workspace's cursor shows only the caller's own rows; an outsider and a switched-off tool; a Document without search columns refused by the database; old wording not found after an edit; 10 000 Documents paged under four orders with uploads in between, a second Workspace of 2 000 beside it — each Document once, slowest request 14 ms), `packages/domain/src/document-search.test.ts` (folding, terms, wildcard escaping, query and cursor validation incl. prototype names such as `toString`), `apps/server/src/http/document.test.ts` (401 without session and `404 workspace_not_found` for an outsider on both routes; Home's Folder and type ids under Office; strict parameters with stable codes; injection strings in `q`, `sort` and `cursor`; no ids, emails or hashes in the body; paging with a Document added in between; nothing searched for in the captured log), `apps/server/src/http/route-security.test.ts` (the new route in the session and non-member sweeps), `apps/web/src/document-model.test.ts` (an address with unknown or malformed filter values is ignored, not passed on), e2e. Mutation checks in steps.md 16.3.
**Secrets/data involved:** titles, notes and tags of Documents (searched, never returned beyond the existing summaries); search words; years, tags and uploader display names as filter values. No credentials.
**Logging review:** no new log output. Search words, tags and uploader names are in the query string, which the request serializer redacts; the test captures the log and finds none of them.
**Authorization review:** HTTP authenticates and parses (`apps/server/src/http/document-routes.ts`); the decision is `authorizeTool` in `packages/application/src/documents/documents.ts`; Workspace scoping, the Trash exclusion and every filter in `packages/database/src/document-repository.ts`.
**Open risks:** (1) **Search words appear in the browser's address** (`…/documents?q=…`), so that Back and reload keep the list: they are in the browser history of that device, and a reverse proxy other than the shipped one may log query strings — operators who add an access log should exclude or redact them. (2) Every member, guests included, can search and filter everything in the Workspace's Documents — consistent with the decision that guests read all Documents (H4); search adds speed, not access. (3) A search reads all searched text of the Workspace: bounded by 50 000 Documents and 4 000 characters of notes (139 ms measured in that worst case), by the page size and by the global rate limit — there is no separate limit for searches. (4) The uploader filter lists display names of people who uploaded Documents that still exist, also of members who have left — the same names the Documents themselves show. (5) Response time still reflects the *own* Workspace's size (inherent). (6) Titles, tags and notes exist a second time in folded form in the database and therefore in backups; they follow the Document (edited with it, in Trash with it, deleted with it in 16.4). (7) Recognised text (16.9) will need its own review: an index shared between Workspaces must not reintroduce the timing dependence rejected here.

### Security check: storage, export and permanent deletion (Step 16.4)
**Threat surface:** *Storage:* one limit now covers two upload paths — exceeding it through the other path, or through two uploads at once; a Workspace admin raising their own limit above what the server admin allows, or a member below admin changing it; a server-admin action reachable by a Workspace admin; a limit that silently deletes when lowered; the change of model reducing what a Workspace could store before; usage figures disclosing another Workspace's content or size. *Export:* a bulk copy of the most sensitive content, open to guests by decision — Documents of another Workspace or in Trash in the archive; ids of another Workspace as scope; an export as a way to exhaust disk reads, memory, file handles or bandwidth (huge selections, many at once, repeated); zip-slip and friends through titles, Folder names and file names (`../`, absolute paths, `CON`, control or bidi characters, names that collide or differ only by case, names that hide the real type); stored XSS in the HTML index when it is opened from disk (a `file:` origin), links that leave the archive or load remote content; a state-changing `GET` triggered from another site; the archive kept somewhere on the server; a truncated archive passing as complete. *Permanent deletion:* the first destruction of user content — by a role that may only restore, by a member of another Workspace, of things that are not in Trash, of more than the confirmation named; by a request forged from another site; by the passing of time; deletion without a trace; files still referenced being removed from disk; a person believing that a purge also erased backups.
**Controls added:** **Storage.** `storageUsageIn` is the single source of "used" and "limit": instruction images (14.3's own rule), Document originals, previews and Trash, grouped by content hash. It runs inside the `IMMEDIATE` transaction of `ImageRepository.register`, `DocumentFileRepository.register` and `addDerivative`, so no combination of concurrent uploads can pass the limit together; reads are never limited. The ceiling is written only by `setCeiling` — ACTIVE server admin, re-checked in the transaction, 100 MB – 1000 GB, `WORKSPACE_STORAGE_CEILING_CHANGED` in the security log, 30 changes per 15 minutes; the Workspace's own limit only by `setLimit` — `workspace.settings.manage` (ADMIN) through `authorizeWorkspace` and again in the transaction, refused above the ceiling by the use-case and by a database trigger, `WORKSPACE_STORAGE_LIMIT_CHANGED` in the audit trail. The limit in force is `min(ceiling, own limit)`. Neither write touches content. The breakdown is returned to Workspace admins (their Workspace) and server admins (all Workspaces: names and byte counts, nothing else); other members get used and limit. **Export.** `document.view` via `authorizeTool`, re-checked with the tool switch inside the transaction that resolves the scope, counts it, reads the plan and writes the audit event; the scope is resolved among **live** Folders and Documents of the route's Workspace — a foreign, unknown or trashed Folder is `404 folder_not_found`, a selection containing any such Document `404 document_not_found` (all or nothing). Bounds before anything is read from disk: 2 GB and 5 000 files (`413 export_too_large`, with the numbers), ≤ 200 selected Documents, one running export per person (`429 export_running`), ten export requests per 15 minutes per person; strict query schema. The archive is **streamed**: nothing is written to the server's disk or held in memory beyond the plan; files are opened lazily, one at a time, from paths built from stored hashes; a file that cannot be read aborts the stream. **Paths:** every segment is produced by `exportSegment` (NFC; white space collapsed; `\ / : * ? " < > |`, control and format characters → `_`; leading and trailing dots and spaces removed, so `.` and `..` cannot occur; Windows device names prefixed; ≤ 80 code points; never empty), files are prefixed with their page number and end in an extension of the **detected** format, and names in one directory are made unique without regard to case; `index.html` and `metadata.json` are reserved at the root; yazl additionally refuses absolute and parent paths. **HTML index:** generated from a fixed skeleton; every value passes `escapeHtml`; links are `./` + percent-encoded segments; no script, form, image, frame or remote reference exists in the generator, and the page carries `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` and `referrer: no-referrer` for when it is opened from disk. The response is `application/zip`, `attachment`, `nosniff`, `no-store`, with a server-generated file name. `GET` is safe here because the session cookie is `SameSite=Strict` (no cross-site request carries it) and the only effects are an audit entry and bounded work. **Permanent deletion.** New capability `document.purge`, ADMIN only (matrix test), checked by `authorizeTool` and again — with the tool switch — inside the deleting transaction; `POST` with the `Origin` check, a strict body that names 1–200 items or says `all`, never both. Only rows that **are in Trash** in the route's Workspace can be named: anything else is "not found" and the whole request changes nothing. A Folder takes exactly what went to Trash with it; other Trash entries inside it are re-parented, not deleted. The delete statements themselves carry `deleted_at IS NOT NULL`, and the triggers `documents_delete_only_from_trash` / `document_folders_delete_only_from_trash` refuse anything else at the database. One audit event per item in the same transaction (subject id, title or name, counts — no notes, no file names, no content). Files are not deleted by the request: housekeeping removes a file only when no row references it and its upload is older than the grace period — the rule that already protected backups. There is no timer, schedule or expiry anywhere that purges. The confirmation dialog states the counts, that it cannot be undone, what the history keeps, and that backups are not affected.
**Negative tests:** `packages/database/src/storage-use-cases.test.ts` (an image refused because of Documents and a Document because of images; exactly one of an image and a file upload on two connections; a ceiling far below usage: nothing deleted, everything readable, nothing accepted; Trash counted and released only after purge **and** housekeeping; EDITOR, USER, GUEST and an outsider on the storage view and limit; export of another Workspace's Folder or Document, of Trash, of mixed selections; hostile titles and file names; too large; a second export while one runs; the slot freed after a failed delivery; no audit event for a refused export), `packages/domain/src/document-export.test.ts` (segments for `..`, absolute and Windows paths, device names, control, bidi and zero-width characters, over-long names; type-hiding file names; collisions; a broken Folder chain), `packages/import-export/src/documents-archive.test.ts` (the archive read back with a strict ZIP reader: originals byte-identical and stored; unsafe paths refused by the writer; an unreadable file ends the stream with an error), `apps/server/src/http/storage.test.ts` (401 / 403 / 404 on every new route for guest, user, outsider and no session; **Secrets/data involved:** everything a Workspace's Documents hold leaves the server in an export — originals with their embedded metadata, titles, notes, tags, names of uploaders, SHA-256 checksums of the files. Storage figures (bytes per tool). No credentials.

**Authorization review:** HTTP authenticates and parses (`storage-routes.ts`, `document-routes.ts`); decisions in `packages/application/src/storage/use-cases.ts`, `documents/export.ts` and `documents/documents.ts` (`purgeDocumentTrash`); in-transaction guards, scoping and the Trash condition in `packages/database/src/storage-usage.ts` and `document-repository.ts`.
**Open risks:** (1) **An export is a complete copy outside the application's control, and guests can make one** (decision P2): once downloaded, VMN's permissions, Trash and deletion no longer apply to it; the audit trail shows who exported what and when. (2) **Permanent deletion is not erasure from backups:** existing backups (hard links in `backups/documents`) keep the file until they rotate, and off-host copies for as long as the operator keeps them — said in the dialog and the documentation. (3) A purged file stays on disk until housekeeping runs and its upload is a day old; it is unreachable through the application meanwhile (no row), but an operator with shell access can still read it. (4) Titles of purged Documents and names of purged Folders remain in the append-only audit trail, by design; a title that is itself the secret cannot be removed. (5) A Workspace admin can empty Trash for everyone — irreversible, audited, and only what members had already deleted. (6) The export rate limit and the one-at-a-time rule are per server process; ten exports of 2 GB per person per quarter of an hour are still possible — a deliberate bulk feature on a self-hosted server, bounded but not cheap. (7) The export reads its plan (up to 5 000 files' worth of rows) into memory; the files themselves are streamed. (8) `index.html` relies on escaping and on containing no active element; its own CSP is defence in depth and is ignored by browsers for some `file:` cases. (9) SHA-256 values of files are disclosed in `metadata.json` to people who receive the files themselves anyway; storage names remain unusable as addresses. (10) The storage breakdown tells a Workspace admin how much Trash holds — content deleted by members they could list in Trash anyway. (11) Links (16.5) and Mail (16.11) will add relationships to exports: they must be filtered by what the exporter may read — the check in §3 stays the gate.
**Reviewed:** 2026-10-02

### Security check: links and Document versions kept for Runs (Step 16.5)
**Threat surface:** a Link as a side door: reaching, naming or counting a record the viewer may not read (another Workspace's Procedure, Schedule, Run or Document; a Document in Trash for a guest; anything of a switched-off tool); creating a Link across Workspaces by combining ids, also below the application; a guest creating or removing Links; a Link changing or deleting the records it connects; reminder messages carrying Document content through a linked Reminder; "Remind me…" creating a Schedule or taking dates from a Document without the person's review; a retained version as a way to rewrite history — changing a finished Run, its snapshot or its audit trail, or silently following later edits of the Document; retained files lost to housekeeping, to permanent deletion of the source or to a backup that no longer holds them; a wrong or sensitive Document kept with a finished Run for ever; retained files escaping the storage limit; a purged Document still named through its Links; unbounded Links.
**Controls added:** **A Link is two ids and nothing else.** No route returns a linked record's content: a Link's view carries kind, id, title and a state, and opening the record goes through that record's own routes with their own authorisation. Reading Links needs the Documents tool switched on, `document.view` and the view capability of the other kind (`procedure.view` / `run.view`); adding or removing needs `document.manage` and read access to the other end, checked by the use-case and again — with the tool switch — inside the `IMMEDIATE` transaction. Every lookup is by Workspace id + id: a Document, Procedure, Schedule, Run or Link of another Workspace is `404 document_not_found` / `link_target_not_found` / `run_not_found` / `link_not_found`, and a list asked from the wrong Workspace is empty. **In the database:** `links_ends_exist` refuses a Link unless both ends exist in the Link's own Workspace (and the type is a known one), `links_identity_immutable` freezes the ends, `run_documents_same_workspace` and `run_document_files_same_workspace` do the same for kept versions, and the composite foreign key ties each kept file to its Workspace. **Disclosure:** a Document in Trash is named to `document.manage` only (those who can open Trash); a Document deleted for good is never named — its end holds only when and by whom; deleted Procedures are shown as deleted by title, as their Runs and audit history already do. Targets that are deleted, in Trash or gone cannot be linked. **Reminders:** a linked Reminder is an ordinary Schedule created through the existing use-case (`schedule.manage`, existing limits and recipients); its messages are unchanged and contain nothing of a Document. "Remind me…" proposes only a title and creates nothing before the person confirms the schedule dialog. **Kept versions:** linking writes only to `run_documents` / `run_document_files` and one audit event with the Run's id — no statement touches `runs`, `run_sections`, `run_steps` or earlier events (tested by comparing the rows before and after); the rows are immutable by triggers and deletable only while the Run is ACTIVE (use-case check and trigger — P4 interim rule). The version copies the Document's details and references its files, which are immutable and content-addressed; the reference is part of the single rule that decides what housekeeping may delete and what a backup must hold, and the files are charged to the Workspace's storage ("kept for executions" once no Document holds them). Files are served by the existing document-file routes: `document.view`, Workspace + file id. **Purge:** marks the Document's end of every Link as gone in the same transaction (a trigger refuses the deletion otherwise) and leaves kept versions untouched. **Bounds:** 50 Links per Document, 20 Documents per Run, strict bodies and query (exactly one of `procedure` / `schedule`).
**Negative tests:** `packages/database/src/link-use-cases.test.ts` (guest cannot link, unlink or keep; outsider gets nothing; every cross-Workspace combination for Document, Procedure, Schedule, related Document and Run, in both directions; the same by raw `INSERT`, plus an unknown type and a non-existent Document; ends cannot be updated; role lost between check and write; tool switched off; targets deleted or in Trash refused; Trash title withheld from a guest and shown to a manager; purged Document unnamed, with when and by whom; a Link with both ends purged removed; the Run's row, Steps, detail and earlier events byte-equal before and after linking; the kept version unchanged through retitle, replaced page, Trash, purge and two housekeeping runs past the grace period, files compared by SHA-256; removal from a finished Run refused for USER and ADMIN and by raw SQL; kept rows cannot be updated; storage line and total), `apps/server/src/http/link.test.ts` (401 / 403 / 404 with stable codes on every route for guest, outsider, no session and missing `Origin`; strict bodies and queries; no ids, emails or hashes in responses; kept file served byte-identical to a guest and 404 to another Workspace; the Run's history gains one entry; nothing of a Document in the captured log), `apps/server/src/http/route-security.test.ts` (seven new routes in the session, non-member, child-id and malformed-id sweeps, with a real Link and a real kept version), e2e.
**Secrets/data involved:** titles of Documents, Procedures and Reminders as Link labels; a copy of a Document's details (title, type, dates, notes, tags) and references to its files, kept with a Run beyond the Document's own life. No credentials.
**Logging review:** no new log output. Audit metadata: the Document's title, the linked record's kind, id and title; for a kept version the Document's id, title and number of files — never notes or content.
**Authorization review:** HTTP authenticates and parses (`apps/server/src/http/link-routes.ts`); decisions in `packages/application/src/links/use-cases.ts`; in-transaction guard, tool re-check, scoping and the lifecycle rules in `packages/database/src/link-repository.ts`; database triggers in migration 0031.
**Open risks:** (1) ~~P4 is undecided~~ — decided and implemented on 2026-10-02: see "Security check: removing a kept Document version from a finished Run (P4)" below. (2) **A kept version defeats permanent deletion of its content by design** (H10): purging the Document does not remove what a Run keeps, and the purge confirmation does not yet say so per item. (3) Notes and tags are copied into the kept version and stay readable to every member through the Run. (4) Titles of linked records persist in audit metadata. (5) With the Documents tool switched off, kept versions are hidden with the tool; the Run's history entry "linked the document …" stays visible with the title. (6) "Remind me…" is two requests: if linking fails after the Schedule was created, the Schedule exists without the Link. (7) A deleted Procedure remains named on Documents it was linked to — as in its Runs. (8) Future record types (Contacts, Maintenance, Equipment, Mail) extend the triggers; Mail and anything guests may not read need per-viewer filtering of Link lists — not built, because every current target is readable by every member.
**Reviewed:** 2026-10-02

### Security check: removing a kept Document version from a finished Run (P4, Step 16.5)
**Threat surface:** the one way to take something out of a finished Run's record — and therefore the one place where "history is immutable" has an exception: removal by someone who is not a Workspace admin, by an admin of another Workspace, or through a request forged from another site; removal without a deliberate decision (a stray click, a replayed request); removal that leaves no trace, or a trace that can later be edited away; a removal note that itself keeps the sensitive content it was meant to remove (title, notes, file names, ids that lead back to the files); the removed files still reachable by their ids; a removal that damages more than it names — the original Document, versions other Runs keep, the Run's Steps or its earlier history; files deleted from disk while something still needs them; storage figures that no longer match what is stored; the belief that backups were cleaned as well.
**Controls added:** **Who:** new capability `run.document.remove`, ADMIN only in the central table; the use-case checks membership, the Documents tool switch and the capability, and the repository re-checks the actor's current role and the tool inside the `IMMEDIATE` transaction. Server admins who are not Workspace admins have no such right. **Deliberate:** `POST` with the `Origin` check; a strict body whose `confirm` must be the literal `true` and whose `reason` is required — 1–500 code points of plain text, control and bidi characters refused; the dialog disables its button until a reason is typed and "I understand that this cannot be undone" is ticked. **Scope:** the version is looked up by Workspace id + Run id + version id; a version of another Workspace or another Run, an unknown or already removed one is `404 link_not_found`; an ACTIVE Run is `409 run_still_active` (the ordinary removal applies there, unchanged). **Trace:** the removal writes, in the same transaction, a row in `run_document_removals` (who, when, why; when and by whom the version had been linked; number of files) and the audit event `RUN_DOCUMENT_REMOVED` with the Run's id. Notes can never be updated or deleted (triggers), audit events are append-only as always. **No content in the trace:** neither the note nor the event holds the title, type, dates, notes, tags, the source Document's id, file names or file ids — asserted by a test that searches the stored rows and the API answer for each of them. **The database enforces the rule:** a kept version of a finished Run can only be deleted when its removal note exists (`run_documents_delete_needs_note`, `run_document_files_delete_needs_note`), and a note can only be written for an existing version of a finished Run of the same Workspace. **Access ends at once:** the version disappears from the Run's listing, from the Document's Linked section and from exports; for each of its files that nothing else references (no Document page, no other Run's version) the file row and its preview rows are deleted in the same transaction, so the document-file routes answer 404 for it immediately. **Nothing else is touched:** files still referenced elsewhere keep their rows; the transaction issues no statement against `runs`, `run_sections`, `run_steps`, `documents`, `document_pages`, other `run_documents` or earlier `audit_events`. **Storage** is computed from the rows, so it drops exactly by what was released and not at all while another reference remains; the bytes are removed from disk by housekeeping under the unchanged rule (no row uses the hash, grace period passed).
**Negative tests:** `packages/database/src/link-use-cases.test.ts` (USER, guest, an outsider, and another Workspace's admin with these ids; a role lost between the use-case's check and the transaction; missing confirmation; empty, blank, over-long and bidi reasons; a version of another Run; an ACTIVE Run; raw `DELETE` of a finished Run's version without a note; raw `UPDATE` / `DELETE` of a note; the trace searched for title, notes, tags, file name, Document id and file id; Run row, Steps, detail and earlier events compared before and after; the other Run's version compared by SHA-256; the Document's title, pages and revision; storage unchanged while another Run needs the files and reduced when the last reference goes; the released file refused at once, the Document's own page still served; bytes gone only after housekeeping), `apps/server/src/http/link.test.ts` (401, 403 for USER and guest, 403 without `Origin`, 404 for an outsider and for the ids under another Workspace; `{}`, missing `confirm`, `confirm: false`, `confirm: "yes"`, missing reason and an extra field → `400 invalid_request`; reason rules with stable codes; nothing removed by refused requests; the listing and the history afterwards), `apps/server/src/http/route-security.test.ts` (session, non-member, child-id and malformed-id sweeps), `packages/permissions/src/policy.test.ts` (ADMIN only), e2e (dialog wording, disabled button, note, no download links). Mutation checks in steps.md.
**Secrets/data involved:** the reason (free text, kept permanently, readable by everyone who can see the Run); display names of who linked and who removed. The removed version's details and files are what the operation takes away.
**Logging review:** no new log output; the reason travels in the JSON body, which is not logged.
**Authorization review:** HTTP authenticates and parses (`link-routes.ts`); decision in `removeRunDocumentFromFinishedRun` (`packages/application/src/links/use-cases.ts`); in-transaction guard, scoping, the note and the release of files in `removeFromFinishedRun` (`packages/database/src/link-repository.ts`); triggers in migration 0032.
**Open risks:** (1) **The earlier history entry keeps the Document's title:** `RUN_DOCUMENT_LINKED` was recorded with the title when the Document was linked, and audit history is never rewritten — a title that is itself sensitive stays readable in the Run's history. The dialog says so. Removing that would mean rewriting an audit event, which this project does not do; it would need its own decision. (2) **Backups are not cleaned:** existing backups keep the files and the removed rows until they rotate, and off-host copies as long as the operator keeps them — stated in the dialog and in `deployment.md`. (3) A released file's bytes stay on disk until housekeeping has run and the grace period has passed: unreachable through the application, readable with shell access. (4) The reason is whatever the admin writes; the field asks not to describe the document. (5) A Workspace admin can remove evidence from finished Runs: by decision; every removal leaves a permanent, visible note and a history entry, and cannot be done silently. (6) Files that are still pages of the Document remain available through the Document — the removal concerns the Run's copy, not the Document. (7) With the Documents tool switched off, notes are hidden with the rest of the tool (the history entry stays), and removal is not possible until it is switched on.

### Security check: Contacts (Step 16.6)
**Threat surface:** personal data of people who are not users and never agreed to anything (names, numbers, addresses), visible to every member of a Workspace; a new permission boundary and tool switch; reading or changing Contacts of another Workspace through an id, a search, a cursor, a duplicate hint, a link or an import; a guest changing or bulk-exporting them; **two parsers of files from anywhere** (CSV, vCard) — oversized or deeply quoted input, wrong encodings, folded and quoted-printable lines, embedded photos, text that pretends to be a second card; an import that saves before it is confirmed, or saves something other than what was shown; **exports opened by other programs** — spreadsheet formulas in CSV, values that break out of a vCard property; **stored values that become links** — `javascript:` or `data:` websites, `tel:` / `mailto:` with injected parameters; names that reorder text; data that outlives a permanent deletion in history, links, logs or duplicate keys.
**Controls added:** **Permissions:** `contact.view` (all roles), `contact.manage` and `contact.export` (USER and above), `contact.purge` (ADMIN) in the central table (exact-matrix test). Every use-case goes through `authorizeTool` (membership → tool switch → capability); every write runs in an `IMMEDIATE` transaction that re-checks the actor's current role and the switch. A switched-off tool is `404 tool_not_enabled` on every route for every role, and Contact links disappear from Documents. **Isolation:** every query starts with the route's Workspace id; ids of another Workspace, of Trash (for live routes) and unknown ids are the same `404`; duplicate lookups are scoped twice (keys and Contacts); a cursor is only a position inside the Workspace's own listing; the Link trigger refuses a Contact, Procedure or Document of another Workspace whatever code asks. **Validation** (domain, and again as CHECKs for the bounds and the website): names and labels without control or bidi characters; phone numbers of digits and formatting characters only; email addresses by the account rule; websites only absolute `http` / `https` without credentials. **Links:** `tel:` is built from digits and `+` only, `mailto:` from a percent-encoded checked address, both on the server; the client renders a link only when it matches the expected scheme and shape, and websites open with `noopener noreferrer`. All values are rendered as text by React; nothing is HTML. **Import:** the body is not inspected and the file not parsed until the actor is authorised (test with a counting parser); 1 MiB (enforced by the body limit and again by the decoder), 1000 contacts, 10 000 characters per value, 300 columns, at most 5000 rows read; strict structure (unclosed quotes, text outside a card, unclosed or nested cards refuse the whole file with a stable code and line — never content); unknown or binary properties are skipped without decoding; quoted-printable is decoded as text only; the preview writes nothing; the second request carries the confirmed entries and every one is normalised again — all or nothing, bounded by the Workspace limit of 10 000. Preview requests are rate-limited per person. **Export:** `contact.export` re-checked in the transaction that reads the Contacts and writes the audit event; always a download (`attachment`, `nosniff`); CSV neutralises leading `= + - @`, tab, CR and `'`, doubles quotes; vCard escapes `\ , ;` and line breaks and folds by bytes — a value cannot start a property or a card. Rate-limited. **Privacy of history:** Contact audit events hold ids and counts only; Document-link events omit a Contact's name; a Contact in Trash or deleted for good is "a deleted contact" on linked records. Permanent deletion removes the row and its keys and marks its Links in one transaction; a test then searches every table for each of the person's values. **No Contact value is logged** (test over the captured server log).
**Negative tests:** `packages/database/src/contact-use-cases.test.ts`, `apps/server/src/http/contact.test.ts`, `apps/server/src/http/route-security.test.ts`, `packages/import-export/src/contacts.test.ts`, `packages/domain/src/contact.test.ts`, `apps/web/src/contact-model.test.ts`, `packages/permissions/src/policy.test.ts`, e2e — listed with the mutation checks in steps.md 16.6.
**Secrets/data involved:** names, organisations, phone numbers, email and postal addresses, websites and free-text notes of third parties. No credentials.
**Logging review:** no new log output. Import files travel as request bodies and export files as response bodies, neither of which is logged; search words are in the query string of `GET …/contacts?q=` and therefore in the access log like every query string (as for Documents, 16.3) — a searched name or number can appear there.
**Authorization review:** HTTP authenticates and parses (`contact-routes.ts`); decisions in `packages/application/src/contacts/use-cases.ts` (and `links/use-cases.ts` for Document ↔ Contact); in-transaction guards, scoping and audit in `packages/database/src/contact-repository.ts`; database triggers in migration 0033.
**Open risks:** (1) **Every member, guests included, sees every Contact** — by decision; there are no private Contacts. (2) **An export is a complete copy outside the application** (USER and above); it is audited, not prevented. (3) **Search words reach the access log** (see Logging review). (4) Backups keep deleted Contacts until they rotate. (5) Formula neutralisation protects spreadsheet programs that honour a leading apostrophe; a program that strips it and evaluates the rest is outside VMN's control. (6) A `tel:` or `mailto:` link hands a value to another program on the person's device; VMN restricts what the value can contain, not what that program does. (7) The website of a Contact is whatever `http(s)` address a member entered — it may be a malicious site; it opens in a new tab without access to VMN. (8) Duplicate detection is a hint with known blind spots (misspelled names, national vs. international numbers) — nothing relies on it. (9) vCard and CSV are read by parsers written for this project (no dependency was added): small, bounded, strict and fuzzed, but not battle-tested like a library; they only ever produce plain strings that then pass the same validation as typed input.
**Reviewed:** 2026-10-02

## 14. Outbound connections to configurable hosts (SSRF policy)

_Policy defined 2026-10-01 (steps.md 16.0); no code uses it yet. It is a prerequisite: no feature may open a connection to a host supplied through the application before it follows this section and has its own "Security check". First planned user: Mailboxes (16.10, IMAP/SMTP — its threat model is written there, task 2). Webhooks, ntfy and Gotify would fall under it as well._

### Scope
- **Covered:** every connection the server opens to a host name or address that a user or admin entered through the UI or API (any role, including server admins) or that arrives in content (a URL in a file, a message, an import).
- **Not covered:** hosts fixed in the code (`api.telegram.org`, 13.7) and hosts set by the operator in the server's own configuration (the SMTP relay of 9.1, which may be a loopback or private relay by design). They keep their own controls. A setting that moves from operator configuration into the UI becomes covered.
- **Content never causes a connection:** no URL found in a Document, extracted text, mail or import is fetched by the server. Remote images in mail are loaded — if at all — by the viewer's browser after an explicit action, never by the server (§5).

### Rules
- [ ] **Public addresses only** (H20). The server resolves the host itself and classifies **every** returned address, A and AAAA. A connection is allowed only if all of them are public global unicast addresses; if any is not, the host is refused as a whole. Classification is an allow-list of "public", not a deny-list. Refused in particular: unspecified (`0.0.0.0/8`, `::`), loopback (`127.0.0.0/8`, `::1`), private (`10/8`, `172.16/12`, `192.168/16`), CGNAT (`100.64/10` — also Tailscale), link-local incl. cloud metadata (`169.254/16`, `fe80::/10`), unique-local and site-local (`fc00::/7`, `fec0::/10`), multicast and broadcast, reserved, benchmarking and documentation ranges, and every IPv6 form that embeds an IPv4 address — IPv4-mapped (`::ffff:0:0/96`), NAT64 (`64:ff9b::/96`), 6to4 (`2002::/16`), Teredo (`2001::/32`) — which is judged by the embedded address or refused.
- [ ] **No second resolution (DNS rebinding):** the connection is opened to the exact address that was validated, with the original host name used only for TLS (SNI and certificate verification). Every new connection — reconnects and retries too — resolves and validates again; a result is never cached as "safe".
- [ ] **Host input is strict:** a syntactically valid DNS name (IDNA-normalised) or a canonical IP literal, classified by the same rules; other numeric forms (decimal, octal, hexadecimal, shortened IPv4), names without a dot, trailing garbage, embedded credentials, paths and control characters are refused before any lookup. `localhost` and single-label names are refused.
- [ ] **Ports are an allow-list per feature**, fixed in that feature's Security check (Mail: the standard IMAP and mail-submission ports only). No free port choice — it would turn the server into a port scanner.
- [ ] **TLS is mandatory:** implicit TLS or STARTTLS, TLS ≥ 1.2, certificate verification against the host name; cleartext and STARTTLS downgrade are refused; there are no certificate exceptions.
- [ ] **No redirects or referrals** are followed, in any protocol. An HTTP-based feature treats a redirect as a failure.
- [ ] **Bounded:** connect, handshake and idle timeouts; response and message size caps; a limit on connections per target and per Workspace; reconnects with backoff and a bounded number of attempts.
- [ ] **Not an oracle:** refusals and failures are reported with a small set of stable codes that do not tell whether an internal host exists, which address a name resolved to, or whether a port is open; resolved addresses are neither returned nor logged. "Test connection" and every action that causes a connection are rate-limited per user and per Workspace (persisted limits).
- [ ] **Who may configure a target** is an explicit capability reviewed per feature and re-checked in the write transaction; a target is accepted only in a JSON body. The instance admin can switch each outbound feature off for the whole server.
- [ ] **One implementation:** a single module resolves, classifies and connects; features use it through a port and never open sockets or call a mail or HTTP library with a raw host themselves. A test guards this as `sql-safety.test.ts` guards SQL.
- [ ] **Credentials for a target** follow §9: sealed at rest, bound to their record, never returned, logged or placed in errors or audit metadata; a library error that could embed them is mapped to a stable code (as the Telegram adapter does).

### Required negative tests (with the first feature)

### Limits of this policy
- It protects the server's network position (internal services, the Docker network, the host, a VPN, cloud metadata). It does not make the remote server trustworthy: everything received from it is hostile input (§5).
- **Mail servers on a LAN, reachable only through a VPN, or on private addresses cannot be connected** (H20). The same applies to a self-hosted ntfy or Gotify on a private address. Allowing private targets would be a new product decision and a new review — not a configuration switch added while implementing.
- Egress filtering by the operator (firewall, container network) is useful defence in depth and is documented in `deployment.md` when the first feature ships; the application must be safe without it.
- A public host can still be an unintended target (another customer of the same provider, a public service used as a relay). The port allow-list, mandatory TLS with verification and rate limits bound this; it is not eliminated.
