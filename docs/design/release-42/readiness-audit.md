## Design gaps and scope boundaries

Before application work, a separate prototype/specification should answer these questions:

1. **Contextual interaction:** how people discover and open tools/actions; persistent orientation and labels; what remains reachable when focused; dismissal, Back, Escape and focus return; desktop pointer/keyboard and phone touch behavior. No gesture-only or hover-only action. Search and the plus control in the image are exploratory: there is no inspected shared cross-tool search/command service; the current `AddChooser` offers four capability-filtered creation flows, not every tool. A future cross-tool search needs an explicit scope and per-result authorization/privacy review.
2. **Complete feature map:** account/profile/security, Workspace selection/settings/membership/plugins/storage/backup, history, Trash, imports/exports, instruction images, linked Documents and private/shared Journal must remain reachable alongside all ten navigable tools. Moon is card-only and Gamification is not a destination. The mockup covers only a subset. Define loading, empty, error, guest, disabled-tool, revoked-access, stale-edit and offline states as well as the attractive populated screens.
3. **Accessible composition:** logical reading/tab order independent of planets or animation, visible text labels and focus, explicit state text, 44 × 44 px targets, 320 px no horizontal overflow, phone safe areas/keyboards, zoom/reflow, reduced motion, forced colors and contrast on every painted surface. The mockup's tiny/dim labels, translucent controls and bright horizons are aesthetic reference, not evidence of compliance. Decorative cats/planets must not intercept input or become the only state indicators.
4. **Theme-independent behavior:** demonstrate the same navigation and task controls in the everyday themes and existing scenic themes, with Space optional. Define how a fallback to the existing interface works without losing edits, queued changes, saved order, card choices or theme preferences; no fallback setting or rollout mechanism is approved or implemented by this audit.
5. **Domain fidelity:** the shovel/container/gloves strip does not approve Equipment ownership, inventory, required equipment or a new Step data model. The Attachments tab does not approve arbitrary uploads, completion photos or annotations: existing instruction images and authorized retained Document versions are the available boundaries. New-document counts are illustrative, not approval for a new Today card, tracking scheme or data feed. The cat is optional decoration, not approval to replace the existing named companions or change Gamification.

This review found no application changes in the original PR to assess for runtime regressions. The brief's exploratory limits are consistent with preparation only. Remaining readiness blockers concern an unbuilt design, not demonstrated vulnerabilities in the existing application.

## Security invariants for later work

The current [security policy](../../development/security.md) remains normative; no security behavior was added or changed here.

- Every request still authenticates the current ACTIVE account and authorizes Workspace membership, tool and capability; hidden UI is not a permission boundary. Disabled tools and foreign objects remain unknown, with no result/count/label leaks.
- No broadened response, cache, aggregate, search index or new upload path is justified by a new shell. Private Journal, credentials, own-account preferences/points and Workspace data keep their separate scopes; server-admin status grants no implicit access to shared content.
- Mutations remain explicit, same-origin/CSRF-protected, revision-checked and atomic with required history. No optimistic animation claims a failed or merely queued action was committed. SSE remains Run-specific, authenticated/re-authorized and canonical state is refetched on reconnect.
- Preserve Knot token handling, MFA/recovery flows, sign-out/account-switch storage cleanup, immutable originals/Run snapshots and hostile backup validation. No cloud AI, remote executable plugin, tracking or geolocation is approved.
- Any future change to sensitive flows, storage, query aggregation or preference schema requires the corresponding security-policy update and negative tests before that implementation is complete.

## Suggested sequence and acceptance gates — not execution authorization

1. Separately approve a disposable interaction prototype and complete route/action/role map; evaluate alternatives without choosing the spheres by default. Use fictional data and prove desktop, touch and keyboard access with the existing interface available.
2. Review accessible responsive behavior and feature parity across themes, including degraded/offline and tool-disabled states. Set measurable asset, loading and motion budgets; the 2.27 MB concept PNG is documentation, not a production background or a runtime dependency.
3. Only after explicit implementation approval, plan small presentation changes over existing routes/use-cases, with a reviewed fallback and compatibility strategy. Review any persisted theme/schema changes independently; preserve historical data and backup formats.
4. Before reserving an actual release candidate, rerun full lint/typecheck/unit/browser, dependency audit, schema/upgrade/backup/restore and native amd64/arm64 smoke/scan gates on its exact source. Add navigation/focus/unsaved-work, role/tool isolation, account-switch/queue, theme first-paint, contrast/reflow and reduced-motion checks for the new interface. Include real iOS/Android and screen-reader review; these remain outstanding.
5. Present the special **42nd** milestone, final scope, version, evidence and remaining risks to the owner before publication. No version bump, tag, release workflow, container push, GitHub Release, merge or deployment is part of this preparation. Keep the owner count at 41 until a release is actually published.
